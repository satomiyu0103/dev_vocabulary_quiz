## 1. この文書の位置づけ

### 1.1 目的

[企画書.md](企画書.md) はリポジトリ構成・データスキーマ・実装状態の整理が中心で、**利用者（本人）の学習体験・利用シーン・コンテンツ品質の要望**が十分に書かれていなかった。本書はその不足を補い、**何を満たせば「使いたいクイズ」になるか**を要件として定義する。

### 1.2 読み方

| 文書 | 役割 |
|---|---|
| **本書（要件定義書）** | 利用者要望・機能／非機能・コンテンツ品質・受け入れの基準 |
| [企画書.md](企画書.md) | 背景・データ設計・アーキテクチャ・フェーズ・テスト設計 |
| [DESIGN.md](../../DESIGN.md) | 色・タイポ・コンポーネントのビジュアル正本（UI 実装時に本書と整合） |

実装着手前は **本書 → 企画書 → DESIGN.md** の順で整合を取る。

## 2. 背景と利用シーン

### 2.1 背景

RPA・データ分析の実装では、英単語・API 名・命名の理解がボトルネックになる。汎用の英単語アプリでは「自分が書く・読むコードの文脈」に即した復習が難しい。

開発語彙単語帳（schema v2）でカードを整備したが、当初の Gem 採点は不安定で学習に向かない。**ブラウザ上で確実に採点できる 4 択クイズ**を正本の復習手段とする。

### 2.2 主な利用シーン

| シーン | 条件 | 利用者が求めること |
|---|---|---|
| **移動中の暇つぶし** | スマホ・電波が不安定な場所 | すぐ開ける・軽い・止まらない・片手で押せる |
| **実装前のウォームアップ** | PC・短時間 | 日常英語とプログラミング英語をセットで思い出す |
| **コードを読むとき** | 実装中に単語が出てきた | 「日常ではこういう意味／コードではこう使う」が頭に残る |

## 3. プロジェクト目的

**プログラミングを中心とした英単語の学習**を、ブラウザの 4 択クイズで日常的に続けられるようにする。

具体的には次を達成する。

| # | 目的 | 説明 |
|---|---|---|
| G1 | **二重の意味の定着** | 小中学生レベルの日常英語の意味と、プログラミング文脈での意味をセットで覚える |
| G2 | **文脈での記憶** | 英例文・コード例・解説で「いつ・どう使うか」を確認し、想起のフックを増やす |
| G3 | **手軽な継続** | URL を開くだけ・通信が軽い・操作が直感的で、移動時間でも続けられる |
| G4 | **採点の確実性** | 同じ操作で常に同じ正誤（LLM 採点に依存しない） |

## 4. 対象ユーザー

| ユーザー | 説明 |
|---|---|
| **主利用者** | 本人（RPA / DS 開発の学習者） |
| **副次利用者** | 就活・ポートフォリオで「実プロジェクト由来の語彙学習」を説明する際の参照者 |

前提: 日本語 UI。英語は学習対象語・例文として表示する。

## 5. 用語定義

| 用語 | 定義 |
|---|---|
| **日常の意味** | 小中学生レベルの日常英語としての意味（`meaning_general_ja`） |
| **プログラミングでの意味** | コード・API・命名の文脈での意味（`meaning_programming_ja`） |
| **英→日問題** | 英単語（または英語のヒント）を見て、日本語の意味を 4 択で選ぶ |
| **日→英問題** | 日本語の意味を見て、正しい英単語（`term`）を 4 択で選ぶ |
| **解説パネル** | 回答後に表示する正誤・例文・コード例・補足説明のまとまり |
| **出題プール** | 選択中モードで出題候補となるカードの集合 |
| **カード** | schema v2 の 1 語（または命名パターン）1 レコード |

## 6. 機能要件

各要件に ID を付与する。**状態**は 2026-09-06 時点の実装との差分。

### 6.1 クイズ出題

| ID | 要件 | 詳細 | 状態 |
|---|---|---|---|
| FR-01 | **ランダム出題** | 出題プールから無作為に 1 問選び、同一セッション内で同じカードの即時再出題を避ける（枯渇時はプールをリセットして継続） | 実装済 |
| FR-02 | **4 択回答** | 常に 4 つの選択肢から 1 つを選んで回答する | 実装済 |
| FR-03 | **日→英問題** | 日常の意味・プログラミングでの意味（日本語）を提示し、正しい英単語（`term`）を選ばせる | 実装済 |
| FR-04 | **英→日問題** | 英単語（`term`）を提示し、日本語の意味（日常／プログラミングのいずれかまたは両方）を 4 択で選ばせる | **未実装** |
| FR-05 | **出題形式の切替** | 日→英のみ／英→日のみ／両方ランダム、のいずれかを利用者が選べる（またはセッション内で自動ミックス） | **未実装** |
| FR-06 | **誤答の質** | 似た語・混同しやすい語（`confusable_with` 等）を誤答候補に優先する | 実装済 |

### 6.2 学習コンテンツの提示

| ID | 要件 | 詳細 | 状態 |
|---|---|---|---|
| FR-10 | **語彙の中心** | 日常英語（小中学生レベル）とプログラミングで使う英単語・API 名・命名を中心に出題する | データ済・モードで一部未カバー |
| FR-11 | **二重の意味の確認** | 解説パネルで「日常の意味」と「プログラミングでの意味」の両方を確認できる | 実装済 |
| FR-12 | **英例文** | 自然な英例文と日本語訳を確認できる（テンプレ一括文は不可） | 一部改善済・品質基準は本書 §8 |
| FR-13 | **コード例** | 実際のコード断片と、**いつ・どの場面で・何のために使うか**の解説を確認できる | 一部改善済・品質基準は本書 §8 |
| FR-14 | **記憶のフック** | 例文・コード例は「単語の定義の繰り返し」ではなく、使用場面・効果が伝わる内容にする | **要継続改善** |

### 6.3 モード・ナビゲーション

| ID | 要件 | 詳細 | 状態 |
|---|---|---|---|
| FR-20 | **学習モード選択** | 基本語彙・単体汎用名の注意・ライブラリ/API など、学習テーマで出題プールを切り替えられる | 実装済（3 モード） |
| FR-21 | **トップへ戻る** | いつでも最初の画面（モード選択・再開）に戻れる | 実装済（再読み込み） |
| FR-22 | **進捗の見える化** | 現在モードでの出題済み数／総語数が分かる | 実装済 |
| FR-23 | **次の問題** | 回答後にワンタップで次問へ進める | 実装済 |

### 6.4 データ読み込み

| ID | 要件 | 詳細 | 状態 |
|---|---|---|---|
| FR-30 | **通常読み込み** | 同梱 JSON を取得してクイズを開始する | 実装済 |
| FR-31 | **読み込み失敗時** | ネットワークや `file://` 失敗時、手動で JSON を選んで開始できる | 実装済 |

### 6.5 将来検討（本書 v1.0 では必須としない）

| ID | 要件 | 優先度 |
|---|---|---|
| FR-F1 | 正答率・学習日数の記録（`localStorage` 等） | 中 |
| FR-F2 | 間隔反復（SRS）による「今日やる分」 | 中 |
| FR-F3 | タイピング想起・穴埋めなど出題形式の追加 | 低 |
| FR-F4 | P2 / pattern / DS カテゴリのモード追加 | 中 |

## 7. 非機能要件

### 7.1 性能・信頼性

| ID | 要件 | 詳細 | 目標・判定 |
|---|---|---|---|
| NFR-01 | **接続が軽い** | 静的 HTML + JSON のみ。初回表示に必要な転送量を小さく保つ | 追加の大型 JS フレームワークは導入しない（現行方針） |
| NFR-02 | **止まらない** | クイズの採点・次問遷移はサーバ不要で完結する | オフライン（一度読み込み後）でも連続出題可能 |
| NFR-03 | **決定的な採点** | 同一の選択に対し常に同じ正誤 | LLM・外部 API に依存しない |
| NFR-04 | **読み込みの明示** | JSON 取得中・失敗時に利用者が次の操作を判断できる | エラー時に代替手段（ファイル選択）を提示 |

### 7.2 ユーザビリティ（UX）

| ID | 要件 | 詳細 |
|---|---|---|
| NFR-10 | **スマホで見やすい** | 移動時間の利用を主シーンとする。1 カラム・十分な文字サイズ・行間・タップ領域 |
| NFR-11 | **直感的なボタン配置** | 4 択は縦並びなど迷わない配置。主要操作（回答・次の問題・モード）は親指で届く |
| NFR-12 | **視認性** | 問題文と選択肢・補足文のサイズ・ウェイト差を明確にし、読み飛ばししやすくする |
| NFR-13 | **余計な文言を出さない** | 利用者向けに不要な内部経緯（例: Gem 不要の説明）は表示しない |

### 7.3 アクセシビリティ

| ID | 要件 | 詳細 |
|---|---|---|
| NFR-20 | **色弱フレンドリー** | 正誤の伝達を色だけに依存しない（文言・アイコン・枠線など併用） |
| NFR-21 | **コントラスト** | 本文・ボタン・背景のコントラスト比を WCAG 2.1 の AA 目安（4.5:1 前後）に近づける |
| NFR-22 | **フォーカス表示** | キーボード操作時にどのボタンが選ばれているか分かる |

### 7.4 セキュリティ・運用

| ID | 要件 | 詳細 |
|---|---|---|
| NFR-30 | **公開前提** | `public/` は全世界公開。秘密情報・個人情報を含めない |
| NFR-31 | **安全な DOM 更新** | ユーザー入力は想定しないが、表示更新は `textContent` / 安全な DOM API を優先 |
| NFR-32 | **配信** | Cloudflare Pages 等の静的ホスティング。ビルドコマンドなしでデプロイ可能 |

## 8. コンテンツ要件（データ・表示文言）

機能要件 FR-10〜FR-14 を満たすための**カードデータと UI 文言**の基準。

### 8.1 英例文（`examples_general`）

| ID | 要件 |
|---|---|
| CR-01 | その単語の**日常英語として自然な**用法の例文である（テンプレ `The X is on the table.` の一括生成は禁止） |
| CR-02 | 日本語訳は例文の意味と一致する |
| CR-03 | プログラミング用語の例では、日常英語の用法とコード文脈の用法を混同しない |
| CR-04 | `anti_pattern` カードでは「日常では普通に使えるが、コードでは単体名を避ける」など、**禁止理由が伝わる**例にする |

### 8.2 コード例（`examples_code`）

| ID | 要件 |
|---|---|
| CR-10 | インポート文だけ、変数宣言だけなど**文脈のない断片のみ**は不可 |
| CR-11 | **何ができるか・どのメソッド／属性と組み合わせるか・典型的な使用場面**が分かるスニペットにする |
| CR-12 | `note_ja`（または同等フィールド）に、上記の解説を日本語で書く |
| CR-13 | 可能なら実プロジェクト・よくあるライブラリ用法に即した内容にする |

### 8.3 表示ラベル（UI 文言）

| ID | 要件 | 現状 | 改修後 |
|---|---|---|---|
| CR-20 | プログラミング文脈の補足見出し | 「プロでの使われ方」 | **「コードもしくはプログラミングでの使われ方」** |
| CR-21 | モード名 | 「単体の汎用名」等 | 単体禁止と複合名 OK の区別が伝わる名称を維持 |
| CR-22 | サブタイトル | Gem 言及あり（削除済） | 学習目的が一言で伝わる文言のみ |

### 8.4 データ整合性

| ID | 要件 |
|---|---|
| CR-30 | 統合 JSON の `id` はユニーク（`len(cards) == len(unique id)`） |
| CR-31 | `meta.card_count` と配列長が一致する |

## 9. 現状の課題と改善案

動作確認フィードバック（2026-09-06）と本書作成時点の整理。

| # | 課題 | 原因（推定） | 改善案 | 対応要件 |
|---|---|---|---|---|
| I-01 | 英例文が不自然・意味がおかしい | テンプレ一括生成 | **単語ごとに適した例文を作成・レビュー** | CR-01〜04, FR-12 |
| I-02 | 「プロでの使われ方」が日本語として不自然 | UI ラベルの仮文案 | **「コードもしくはプログラミングでの使われ方」に変更** | CR-20 |
| I-03 | コード例がインポートだけで役に立たない | データ投入時の最小スニペット | **使用場面・使われ方の解説（`note_ja`）を必須化** | CR-10〜12, FR-13 |
| I-04 | 見た目・操作感が「微妙」 | 要件定義不足のまま実装 | **本書の NFR・DESIGN.md を反映した UI 改修** | NFR-10〜13, DESIGN.md |
| I-05 | 英→日問題がない | 企画書が日→英のみ想定 | **FR-04, FR-05 を実装** | FR-04, FR-05 |
| I-06 | 色だけで正誤が伝わる可能性 | フィードバック UI の設計 | **文言・枠・アイコンを併用** | NFR-20 |
| I-07 | 出題統計が実枚数とずれる | JSON `id` 重複 | **配布前検証で重複除去** | CR-30, CR-31 |

## 10. 制約・前提

### 10.1 本タスクの制約

- **本書の作成のみ**。コード・データの改修は別タスクで行う。

### 10.2 システム制約

| 制約 | 内容 |
|---|---|
| 静的サイト | サーバ API・ユーザー認証・サーバ側採点は行わない |
| データ正本 | カード編集の正本は Documents 秘書層 `doc/life/career/dev-vocabulary/` |
| 公開範囲 | クイズ UI・統合 JSON は本リポジトリ `public/` |
| 技術スタック | HTML + CSS + vanilla JavaScript（ビルドなし）を前提 |
| カード編集 UI | 本プロジェクトのスコープ外 |

### 10.3 前提

- 利用者は日本語で UI を操作する
- カードは schema v2 に準拠する
- 新規カード追加ペースは語彙正本側の運用（1 日 5〜15 枚）に従う

## 11. スコープ外（v1.0）

| 項目 | 理由 |
|---|---|
| カード編集 UI | 正本は Documents 側ツール |

| npm ビルド・SPA フレームワーク | 軽量・単純配信を優先 |

## 12. 受け入れ基準（概要）

実装・データ改修タスク完了時に、少なくとも次を満たす。

### 12.1 機能

1. FR-01〜03, FR-06, FR-10〜11, FR-20〜23, FR-30〜31 が動作する
2. FR-04, FR-05（英→日）が実装されたフェーズでは、両方向で 4 択・ランダム出題ができる
3. 解説パネルで日常意味・プロ意味・英例文・コード例＋解説が確認できる

### 12.2 コンテンツ

1. サンプルレビュー（各モード 10 語以上）で、CR-01〜04, CR-10〜12 に違反する例文がない
2. UI ラベル CR-20 が反映されている
3. CR-30, CR-31 を満たす JSON が配布されている

### 12.3 非機能

1. スマホ幅（360px 前後）で 1 問を途切れず回答できる（NFR-10, NFR-11）
2. 正誤が色以外の手がかりでも分かる（NFR-20）
3. 初回ロード後、ネットワーク切断でも連続出題できる（NFR-02）
4. ブラウザコンソールにエラーがない

### 12.4 手動確認手順

[web-local-preview](../../.cursor/skills/web-local-preview/SKILL.md) に従い `public/` で HTTP サーバを起動し、各モードで 1 問以上回答 → 解説確認 → 次問。スマホ幅は DevTools のデバイスモードで確認する。
